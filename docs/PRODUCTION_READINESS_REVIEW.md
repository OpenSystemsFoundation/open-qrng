## Verdict

**Not production ready yet — but closer than it looks.** The engineering quality of what exists is genuinely high: the QASM generation is verified ISA-correct for Heron r2, the CHSH math checks out algebraically, all 395 Jest and 391 Apex tests pass, the UI renders and behaves well in a real org, and the code is clean, formatted, and consistently `with sharing`. The gaps are not sloppiness — they are **unfinished wiring**: the core assignment feature is dead code, the package literally cannot be installed yet, and the security architecture described in ARCHITECTURE.md was never built.

There are **8 release blockers**. None of them are architecturally hard to fix; most are days, not weeks.

### What was verified working (live scratch org)

- App shell loads at `/lightning/n/OpenSF__QuantumFair`; all 5 tabs (Dashboard, Jobs, Setup, Operations, Compliance) render with sensible empty states and no console page errors.
- Canvas circuit diagram draws correctly for the default 8-qubit standard circuit.
- Submitting without an API key fails cleanly with a user-friendly toast (no raw stack traces).
- Setup tab renders the API key entry flow; Operations tab shows sweeper/integrity job controls; Compliance tab shows audit trail + evidence export.

## 1. Release Blockers

These make the product broken, unsafe, or uninstallable for a real customer. Each was independently verified (the first three were confirmed twice — by two different review passes and by direct code inspection).

### B1. The assignment engine is never invoked — the core product loop does not exist

`QuantumAssignmentEngine` (uniform / weighted / subset assignment) has **zero production callers** — it is referenced only by its own test class. The Flow invocable `QuantumRandomAssignment.execute()` discards `recordIds`, `assigneeIds`, `weights`, and `sampleSize`, persisting only `Assignment_Type__c`:

```apex
// QuantumRandomAssignment.cls:151-156
Quantum_Job__c job = new Quantum_Job__c(
    Id = jobId,
    Assignment_Type__c = req.assignmentType
);
update job;
```

When a job completes, `JobProcessor.processSamplerCompletion` parses, validates, certifies, publishes the Platform Event — and stops. No `Quantum_Assignment__c` records are ever created, `FairnessCertificateService.updateAssignmentHash` has zero callers, so `Assignment_Hash__c` (one of the three audit hashes the architecture promises) is always null. Quantum bits are generated, certified, and thrown away. `Quantum_Lead_Round_Robin.flow` even references a pairing flow (`Quantum_Apply_Lead_Assignment`) that does not exist in the repo.

**Fix:** Persist the full assignment request (JSON field on `Quantum_Job__c` or child object) at submission; in `JobProcessor`, after certification, dispatch to `QuantumAssignmentEngine` by type, insert the assignments, and call `updateAssignmentHash` on a canonical serialization.

### B2. Modulo bias breaks the "provably fair" claim (up to 2× skew)

`QuantumAssignmentEngine.cls:36` maps bits to assignees with `Math.mod(value, assigneeIds.size())` and no rejection sampling. For 5 assignees, 3 bits give values 0–7: indices 0–2 get P = 25% each, indices 3–4 get 12.5% each — **the first-listed assignees are twice as likely to win**, deterministically. The Fisher-Yates shuffle (`QuantumAssignmentEngine.cls:158`) has the same defect at nearly every swap (fixed bit width, shrinking modulus), so "unbiased audit sampling" is biased toward low-index records. For a product whose entire value proposition is provable fairness, this falsifies the headline claim.

**Fix:** Rejection sampling — draw `ceil(log2(n))` bits, discard values ≥ n, redraw. Expected overhead < 2 draws. In the shuffle, recompute bit width per swap (`ceilLog2(i+1)`). Document the rejection rule so auditors can replay it.

### B3. Bulk Flow invocations structurally fail; the shipped sample flows can never work

`QuantumRandomAssignment.execute()` loops over requests doing **callout → DML → next iteration's callout**, which throws `CalloutException: You have uncommitted work pending` for every request after the first. Flow batches up to 200 interviews into one invocable call, so any record-triggered bulk insert fails all but one — and the failure is masked by the catch-all, leaving misleading failed-job records. Worse, the packaged sample flows (`Quantum_Lead_Round_Robin`, `Quantum_Case_Routing`) invoke the action from `RecordAfterSave` trigger context, where the trigger's own uncommitted DML makes **the very first callout** throw. The showcased no-code pattern cannot work as shipped, and the flows have no fault connectors so failures are silent.

**Fix:** Make the invocable enqueue a Queueable that performs the callouts (results are async anyway), or restructure to all-callouts-then-all-DML. Add fault connectors to the sample flows.

### B4. No 2GP package exists — nothing can be installed

`sfdx-project.json` has no `packageAliases`; the DevHub contains no `open-qrng` package (verified via `sf package list`). There is no packaging/release workflow in CI and no version ancestry configuration. Compounding this, the package contains **zero `global` Apex**: even after packaging, the `@InvocableMethod` on a `public` class will not appear in subscriber Flow Builder, the `QuantumConsumer` extension interface cannot be implemented by subscribers, and `ComplianceDigestJob`/`ComplianceSummaryJob` cannot be scheduled by anyone (see B7).

**Fix:** `sf package create --name open-qrng --package-type Managed --path force-app`; commit the alias; add a release workflow (`sf package version create --code-coverage`); set `ancestorVersion: "HIGHEST"` after the first promotion. Make `QuantumRandomAssignment` (+ its inner request/result classes and invocable variables) and `QuantumConsumer` `global` **before** the first version — visibility is nearly impossible to walk back later.

### B5. Permission sets grant no Apex class access — the app is dead for its own personas

None of the three permission sets (`QuantumFair_Admin`, `QuantumFair_User`, `QuantumFair_Auditor`) contains a single `<classAccesses>` entry (verified by grep), and none grants read on `Quantum_Job_Complete__e` / `Quantum_Job_Failed__e`. Since `@AuraEnabled` methods require explicit class access, every LWC fails with an access error for any user who isn't an admin with Author Apex — i.e., exactly the users the README's post-install steps produce. The empApi real-time monitoring is likewise dead without Platform Event read access. This is masked in scratch-org development because the default user is a full admin.

**Fix:** Add `classAccesses` per persona and platform-event read permissions to Admin and User sets. Verify with a scratch-org user that has _only_ the packaged permission sets (this should become a standing test).

### B6. No authorization checks on privileged `@AuraEnabled` methods

`SetupController` (the single controller behind all 21 components, 116 `@AuraEnabled` annotations) performs no permission checks anywhere. Because Apex class access is all-or-nothing, any user who can use _any_ QuantumFair component can also call `saveSettings` (overwrite the org's IBM API key and instance CRN), `stopIntegrityCheck` (disable certificate tamper detection), `stopSweeper`, `submitQuantumJob`/`verifyBackendQuantum` (burn the org's QPU budget), and `exportComplianceEvidence`. The `/** Save settings (admin only) */` comment is aspiration, not enforcement. For an audit product, a standard user silently swapping the entropy source's credentials or switching off integrity checking is production-breaking.

**Fix:** Split the controller (admin vs user), ship packaged Custom Permissions (`QuantumFair_Manage_Settings`, etc.) assigned only in the Admin set, and gate each privileged method with `FeatureManagement.checkPermission()`. Log settings changes to `Compliance_Event__c`.

### B7. Stuck-job recovery and compliance digests are off by default and mostly unschedulable

Nothing schedules anything at install: there is no `InstallHandler`. `JobSweeper` (the only mechanism that rescues stranded jobs — and the poller strands jobs easily, see H-R1) starts only if an admin finds the toggle in the Operations tab, and if its self-reschedule ever fails it dies permanently with only a debug log. `ComplianceDigestJob` and `ComplianceSummaryJob` are **never scheduled by any code path at all** — README step 6 promises daily hash digest emails that cannot fire. A compliance officer configuring that email will believe digests are flowing.

**Fix:** Add a `global` post-install handler that seeds org-default settings, the IBM provider row, and schedules the sweeper (or schedule it on first successful key save). Replace the self-rescheduling one-shot cron with a standard recurring cron expression. Wire digest scheduling into the Setup UI or the install handler — or remove the README promise.

### B8. LICENSE file does not exist

The repo claims Apache-2.0 in README, ARCHITECTURE.md ("See [LICENSE](LICENSE)" — a dead link), and its whole open-source positioning, but there is no LICENSE file and no `license` field in package.json. Legally this is all-rights-reserved; no one can safely use, fork, or redistribute it, and the AppExchange listing claim is unsupported.

**Fix:** Add the Apache License 2.0 text as `LICENSE`, plus `"license": "Apache-2.0"` in package.json.

## 3. Medium Priority

- **Weighted CDF selection off-by-one + quantization** — `<=` boundary gives systematic +0.2% skew to earlier assignees; weights quantized to 1/1024; unmatched overflow silently goes to the _first_ assignee. Use integer arithmetic with strict `<`. (`QuantumAssignmentEngine.cls:86-107`)
- **Certificate hash-chain doesn't actually link** — verification recomputes from the cert's own stored previous-hash without comparing against the actual predecessor, and re-certification re-links to the current chain tail creating duplicate positions/cycles. (`FairnessCertificateService.cls:55-92, 214-226`)
- **Sweeper terminal paths are lossy** — Failed jobs in the sweeper publish no failure event; jobs are flipped to Completed _before_ processing (a processing throw strands them Completed-without-certificate, invisible to future sweeps); zombie jobs re-poll every 5 minutes forever. (`JobSweeper.cls:155-198`)
- **Background jobs run `with sharing` as the scheduling user** — with Private OWD, a sweeper scheduled by a non-`viewAllRecords` user silently never sees other users' stuck jobs. Use a documented `without sharing` worker. (`JobSweeper.cls:11, 93-115`)
- **Heap/CPU exposure at documented limits** — sweeper holds up to 10 full result payloads (~1MB+ each at max config) in memory; `vonNeumannDebias`/`concatenateBitstrings` are O(n²) string concatenation. (`JobSweeper.cls:126`, `ResultParser.cls:135-164`)
- **No InstallHandler** (folded into B7 fix) and **no version ancestry** — without `ancestorVersion`, the second release cannot upgrade the first; every early customer would be stranded. (`sfdx-project.json`)
- **manifest/package.xml diverged from source** — wildcards six types with no source (including fossil NamedCredential/ExternalCredential entries) while omitting `CustomApplication`, `Layout`, and critically `RemoteSiteSetting`; any manifest-based deploy produces an org where every callout throws. Regenerate or delete. (`manifest/package.xml`)
- **`saveSettings` admin-only comment unenforced** (folded into B6 fix). (`SetupController.cls:916-967`)
- **Wire errors swallowed in 8 components** — no `{ error }` handling; components sit on empty states forever; `qrngJobMonitor` keeps polling every 5s after errors. (`qrngJobMonitor.js:22-36` et al.)
- **Certificate "View Circuit" modal shows a hardcoded 8-qubit circuit** regardless of the executed one — for an audit tool the displayed circuit must be the real one; the component already computes the right values and never binds them. (`qrngValidationResults.html:248-251`)
- **`qrngChshVisualizer` caches parsed results and never invalidates** when the `@api` prop changes — stale S-value gauge after re-runs. (`qrngChshVisualizer.js:12-24`)
- **empApi subscribe/unsubscribe race leaks CometD subscriptions** — unsubscribe is a no-op if the component detaches before `subscribe()` resolves; job monitors open 2 subscriptions each. (`qrngEventSubscription.js:42-58` et al.)
- **Accessibility** — zero `aria-*` attributes across all 21 templates; canvases have no labels/fallback; the audit-trail modal lacks `role="dialog"`, focus trapping, Escape; `href="#"` links without `preventDefault`. (multiple templates)
- **No devicePixelRatio handling in any canvas renderer** — circuit diagrams, charts, and the certificate visual hash render blurry on every HiDPI display. (`qrngResultsVisualizer.js:152` et al.)
- **Flaky Jest tests** — `qrngJobDashboard` has order-dependent failures (shared mock state); add `clearMocks: true`. CI's Playwright `retries: 2` on a deterministic fixture masks flake instead of surfacing it.
- **E2E PR comments are dead code** — the CLI `--reporter` flag overrides the config's JSON output file, so the results-parsing step always posts "No test results found." (`test.yml:223`, `e2e-debug.yml:44`)
- **Documentation drift** — README/ARCHITECTURE still reference pre-rename objects (`QRNG_Assignment__c`, `QRNG_Log__c`), a `classes/` subdirectory layout that doesn't exist, "314 Jest tests" (actual 395), "7 E2E files ~90 tests" (actual 9 files/147 tests), and ARCHITECTURE.md's package structure omits ~two-thirds of the actual classes. CLAUDE.md documents a husky pre-commit gate that was deliberately removed (dead `lint-staged` config remains).
- **Missing OSS process files** — CONTRIBUTING.md, CODE_OF_CONDUCT.md, CHANGELOG, issue/PR templates, release docs, Dependabot config. `.github/FUNDING.yml` still has template placeholders.
- **`.gitignore` gaps** — `playwright-report/`, `test-results/`, `apex-results/`, `jest-results.json` are untracked-but-unignored.
- **Coverage policy mismatch** — docs mandate 90% per class; CI enforces 75% org-wide; 10 classes are below 90% (`QuantumException` 0%, `IBMQuantumProvider` 65%, `ComplianceEvidenceExporter` 69%, `SetupController` 70%, `IBMQuantumService` 75%, `QuantumRandomAssignment` 76%, `IBMResponseParser` 78%, `IntegrityVerificationJob` 81%, `ComplianceDigestJob` 84%, `JobSweeper` 89%).

## 4. Low Priority (polish)

- Monobit/runs gates use 2σ (α≈4.6%) while docs and the chi-square target α=0.01 — combined, ~1 in 11 perfectly random jobs burns an extra IBM job. Standardize on z ≤ 2.576.
- MCV min-entropy omits the SP 800-90B confidence bound (optimistic estimates near the threshold).
- Certificate hashes cover the `'0x' + hex` encoding, not the bitstring — publish a verification spec (encoding, ordering, truncation, offsets) and reference its version on each certificate; without it third-party replay is guesswork.
- Raw IBM response bodies propagate into user-visible error fields and Aura exceptions — truncate/sanitize.
- Unknown IBM statuses normalize to `Submitted` — jobs burn all polls before failing; treat unknown statuses distinctly.
- One CronTrigger per in-flight job — bursts can hit the 100-scheduled-jobs org limit, and the resulting exception terminally fails jobs (compounds H-R1).
- Inverse `Test.isRunningTest()` guards leave the scheduling/chaining machinery untested — exactly where this review found bugs. Extract a mockable scheduler seam.
- Hardcoded `OpenSF__` strings in empApi channels/payload field access and flow actionNames — centralize.
- `Quantum_Backend_Config__mdt` is dead metadata (zero references) — delete before it's locked into the managed package forever.
- 5 components at API 62 vs 66; error message tells subscribers to edit a Protected custom setting they cannot see; `reduceErrors` duplicated in 5 components with a raw-JSON fallback; `toLocaleString()`/`toISOString()` date handling contradicts user locale on certificates and shifts export defaults near midnight (UTC); NaN propagation in numeric inputs; "Submitted 0 of 3" success toast.
- Workflow hygiene: overlapping push+PR triggers run suites 2–3×, no `concurrency` groups, over-broad permissions.
- Repo hygiene: internal working docs (`FALSE_POSITIVES.md`, `SECURITY_REVIEW_*.md`, dated `2026-03-17-*` plans with hardcoded scratch-org usernames) mixed into the root/docs; `.forceignore` contains dead cargo-culted rules; README "Free on AppExchange" is aspirational and the clone URL is a placeholder; `package.json` lacks `engines`/`license` and double-declares `playwright` + `@playwright/test` at mismatched versions; ESLint covers only `lwc/aura` (e2e/ and scripts/ never linted).

## 5. What's already strong

Credit where due — these are the foundations that make the fixes above worth doing:

- **The quantum core is correct.** The H decomposition `rz(π/2)·sx·rz(π/2)`, CNOT-via-CZ, and Ry decompositions were verified algebraically; CHSH angles and correlator algebra are right in both sampler and estimator paths (S = 2√2 ideal); endianness handling is correct; no PRNG fallback exists in production paths; no customer data ever enters a circuit.
- **Well-layered async design.** Callout-before-DML is handled deliberately, completion logic is centralized in `JobProcessor`, the Schedulable hop sidesteps Queueable depth limits, and failed submissions still leave audit-trail records.
- **Clean security baseline.** All 24 production classes `with sharing`; zero dynamic SOQL (no injection surface); no secrets in code or logs; API key never echoed to the client; hardcoded IBM endpoints (no endpoint injection via records).
- **Real tests.** The Jest suite is largely genuine behavioral testing (wire emissions, toast interception, DOM assertions); Apex tests use proper HTTP mocks; everything passes.
- **Genuinely good end-user docs.** `docs/tutorials/` (18 admin-facing, Flow-based tutorials across 6 industries) is better than most commercial packages ship.
- **The app works.** Verified live: clean rendering, sensible empty states, friendly error handling on the unconfigured path.

## 6. Recommended path to GA

**Phase 1 — Make the product real (blockers B1–B3):** wire the assignment engine into `JobProcessor` with persisted request parameters, rejection sampling for uniform/shuffle/weighted draws, and an async submission path that survives bulk Flow invocation. This is the product; nothing else matters until this loop closes. Add an end-to-end Apex test: submit (mock) → complete → assignments exist → hashes verify.

**Phase 2 — Make it safe (B5, B6, H-S1..3):** class access in permission sets, custom-permission gates on privileged methods, USER_MODE/stripInaccessible on controller reads and user-initiated writes, Private OWD on `Compliance_Event__c`/`Quantum_Provider__c`, and either real Named/External Credentials or honest documentation of the protected-setting design. Then reconcile ARCHITECTURE.md with reality — an auditor reading docs that describe unbuilt protections is itself a trust problem.

**Phase 3 — Make it installable (B4, B7, B8):** create the 2GP package, `global` the extension surface, post-install handler, version ancestry, LICENSE, release workflow. Then an install test in a fresh org with a non-admin user holding only the packaged permission sets.

**Phase 4 — Make it resilient and provable (H-R*, H-M*):** transient-error retries, idempotent completion processing, wall-clock poll budget, truncation guards, per-qubit von Neumann, correct chi-square critical values, revocable certification, CHSH significance margins. Publish the third-party verification spec — it's the feature that justifies the product.

**Phase 5 — Tighten the loop (H-L*, H-C*, H-E1):** the five LWC fixes, CI gating fixes, SECURITY.md, and a scratch-org Playwright smoke project (this review's methodology — `sf org open --url-only` → frontdoor → `/lightning/n/OpenSF__QuantumFair` — works and takes three tests to be transformative: app loads, key saves, jobs render).
